# 步进调用模式设计

## 目标

这份文档讨论一种面向 `tools / skills` 的上下文优化方案：

- 不在初始提示词中一次性暴露全部 skill/tool 细节
- 先只暴露少量关键信息
- 让模型在需要时再逐步展开更详细的信息

这里暂定把这套方案称为：

- 产品/讨论名：`步进调用模式`
- 设计名：`渐进式工具暴露`
- 实现名：`分层工具发现`

这三个名字可以并存：

- 对外说“步进调用模式”
- 设计文档里用“渐进式工具暴露”
- 代码层用“分层工具发现”

## 核心思路

把原本一次性塞给模型的：

- 全量 skills
- 全量 tools
- 完整参数 schema

改成多阶段暴露：

1. 第一阶段：只给名称和简要介绍
2. 第二阶段：模型决定某个大类值得展开
3. 第三阶段：只展开该大类下的候选项
4. 第四阶段：模型确定具体工具后，再获取完整参数 schema
5. 第五阶段：执行真实工具

这不是“把工具藏起来”，而是把工具信息改成按需披露。

## 为什么值得做

当 tools/skills 数量上来后，问题通常不是“模型不会调工具”，而是：

- 初始 prompt 太长
- 大量工具定义占满上下文
- 模型面对很多相似工具时容易混淆
- 参数 schema 很长时，token 消耗非常夸张

因此，`步进调用模式` 的核心收益是：

- 降低初始上下文占用
- 降低 prompt 爆炸概率
- 减少模型在无关工具上的注意力浪费
- 让工具发现过程变成显式可观察行为
- 为后续缓存和权限控制创造更自然的挂点

## 适合的场景

适合：

- 工具数量很多，超过 30 到 50 个
- 工具有明显的领域分组
- 某些工具参数 schema 很长
- skills 数量和说明也逐渐增多

不太适合：

- 工具总数本来就很少
- 工具天然无法分类
- 模型每次都高频跨多个工具域来回切换
- 当前系统尚未完成基础 tool loop

一句话判断：

- 如果现在最大问题是“工具太多导致 prompt 很臃肿”，那就适合做
- 如果现在连统一 Tool 抽象都还没稳定，先别做这个

## 对 skills 的适用性

对 `skills`，这套模式几乎天然成立，而且优先级最高。

推荐做法：

1. 初始 prompt 只给 skill inventory
   - 名称
   - 简短描述
   - 路径或标识
2. 模型判断某个 skill 匹配当前任务
3. 再去读取该 skill 的 `SKILL.md`
4. 只在需要时再打开 skill 里引用的其他文件

这本质上就是：

- `先发现`
- `再阅读`
- `再执行`

对 `skills` 来说，这是最稳的渐进暴露方式。

## 对 tools 的适用性

对 `tools` 也有用，但不能设计得太深。

建议最多做两层半：

1. 顶层分类
2. 分类下工具概览
3. 具体工具的完整参数 schema

不要继续往下做成三层、四层树，否则会带来：

- 决策负担过大
- 工具发现轮次过多
- 模型容易迷路

所以推荐的结构不是“深树”，而是“浅层目录 + 最终 schema”。

## 推荐结构

### 第一层：工具分类概览

提示词里只给：

- 分类名
- 该分类适合做什么
- 可能包含哪些能力

示例：

- `filesystem`: 读取、写入、编辑、检索工作区文件
- `web`: 搜索网页、抓取页面、提取外部信息
- `process`: 执行命令、查看进程、读取运行状态
- `project`: 分析代码结构、查找模块入口、定位引用

### 第二层：分类内工具概览

当模型决定要展开某个分类时，再返回：

- 工具名
- 一句话描述
- 适用场景

示例：

- `read_file`: 读取单个文件内容
- `grep_files`: 在工作区中搜索文本
- `edit_file`: 修改文件指定片段

这里仍然不要返回完整参数 schema。

### 第三层：完整参数 schema

只有模型最终决定调用某个具体工具时，才返回：

- 全量参数
- 参数类型
- 必填项
- 约束

这样模型不会一开始就背负所有参数定义。

## 建议接口

不建议只做一个模糊的 `get_tools_info()`。

更稳的做法是拆成 3 类“发现型元工具”：

### 1. `list_tool_categories`

返回顶层工具分类。

用途：

- 给模型做第一轮粗选择

建议返回字段：

- `name`
- `description`
- `examples`
- `estimated_tool_count`

### 2. `list_tools_in_category(category_name)`

返回某个分类下的工具概览。

用途：

- 第二轮定位具体工具

建议返回字段：

- `name`
- `description`
- `when_to_use`

### 3. `get_tool_schema(tool_name)`

返回某个具体工具的完整参数 schema。

用途：

- 第三轮拿最终调用定义

建议返回字段：

- `name`
- `description`
- `parameters`
- `required`
- `constraints`

### 4. 真实执行工具

执行工具仍然是普通 tool，不要把“发现”和“执行”混成一个接口。

也就是说：

- `list_tool_categories`
- `list_tools_in_category`
- `get_tool_schema`

是发现工具。

而：

- `read_file`
- `edit_file`
- `web_search`

这些才是执行工具。

## Host 侧预筛选

如果完全把分类选择交给模型自己，会有两个问题：

- 它可能选错类
- 它可能反复展开无关类

所以更推荐“半自动”而不是“纯模型自治”。

建议 host 在第一轮先做一次粗筛：

- 按用户请求关键词
- 按当前会话状态
- 按当前工作区
- 按最近工具使用历史
- 或按 embedding / 检索规则

然后只把最相关的 3 到 5 个分类暴露给模型。

这样会比“让模型在所有大类里自由摸索”稳很多。

## 风险

这套模式不是白赚收益，也有明确成本。

### 1. 额外轮次

从：

- 一次性给全量 tool schema

变成：

- 分类发现
- 工具发现
- schema 获取
- 真正执行

调用轮次一定会上升。

### 2. 延迟增加

token 降了，但可能换来更高的决策延迟。

所以它更适合：

- 上下文压力大
- tool 很多

而不是每个简单请求都强制走完整 discovery 流。

### 3. 类目设计失败

如果分类不稳定、边界重叠、命名混乱，模型会更难选。

所以工具分类必须：

- 稳定
- 明确
- 低重叠
- 不要太多层

### 4. 工具跨域组合困难

有些任务天然跨多个域，例如：

- 先查文件
- 再执行命令
- 再做网络请求

如果分类树过于严格，模型可能在多域跳转时变笨。

## 建议采用的策略

推荐分三步推进。

### 第一步：先对 skills 做渐进暴露

这是最稳的：

- 只给 inventory
- 匹配后读 `SKILL.md`

复杂度最低，收益也明显。

### 第二步：对 tools 做“两层发现 + 最后一层 schema”

也就是：

1. 分类概览
2. 分类内工具概览
3. 具体工具完整 schema

不要一开始就做深树。

### 第三步：再考虑 host 预筛选和缓存

等基础行为稳定后，再加：

- 按请求上下文的分类预筛选
- 同会话已展开分类缓存
- 已获取 schema 缓存

这样性能和稳定性会更好。

## 不建议的做法

下面几种设计不建议一开始就做：

- 深层树状工具目录
- 一个万能 `get_tools_info()` 返回巨大 JSON
- 发现和执行混在同一个接口
- 完全依赖模型自己决定所有分类展开路径
- 在底层 Tool 抽象未稳定前就做 discovery 系统

## 推荐命名

如果要正式落地，我建议统一成下面这套命名：

- 方案名：`步进调用模式`
- 技术名：`渐进式工具暴露`
- 模块名：`tool_discovery`

内部概念：

- `tool category`
- `tool summary`
- `tool schema expansion`
- `skill inventory`

这样后续文档、代码、UI 都比较一致。

## 与当前仓库的关系

对当前仓库，建议把这套方案放在基础能力之后，不要抢跑。

推荐顺序：

1. 统一 Tool 抽象
2. tool loop
3. skills inventory
4. 再上 `步进调用模式`
5. 再做 MCP 渐进发现

原因很简单：

- `步进调用模式` 是优化层
- 不是底座层

如果底层 Tool/MCP/Skill 还没稳定，这套优化会把复杂度提前放大。

## 最终建议

这个思路值得做，而且方向是对的。

最值得先实现的是：

1. skill 的渐进暴露
2. tool 的两阶段或三阶段暴露
3. host 侧的轻量预筛选

但要避免：

- 深树
- 全靠模型自己找路
- 过早引入太多 discovery 接口

最小可行版本建议是：

1. 初始 prompt 只给 skill inventory 和 tool category summary
2. 模型可调用 `list_tools_in_category`
3. 模型确定工具后调用 `get_tool_schema`
4. 再执行真实工具

这个版本已经足够验证价值，也不会把系统做得太重。
